# review — owner override, extra round and the merge hand-off

Read by the `review` skill (`skills/review/SKILL.md`) at the points it names: Owner override and Extra round (section 2, step 6), 3.3 (the hand-off) and Click-to-approve (the last section: the owner's "merge", "extra round" and rulings as a click).

## Owner override (rare; only with `owner_approval: chat` in `P config`)

Only for an owner who says they want to dismiss what Claude or Codex would not (an item Claude or Codex's second review made ACCEPT): never offer or ask for it. By default you decide
(`P triage claude-ruling`, SKILL.md Rulings). This path is the only one that loosens an ACCEPT or clears an item Claude may not rule on.
One more case (#559), only when the OWNER raised it: an arbiter or judge ACCEPT that is not fixed yet may be **deferred** (`--decision FOLLOW-UP` only; a typed reject or accept of it is refused). The request line for such an item says it is ACCEPTED, NOT fixed (`notes`), and you show that to the owner. The ruling is bound to the owner's merge, listed in the Rulings block as `by owner deferral (accepted by arbiter)`, and `review-complete` waits for its issue (`followups create --round R`); it cannot be undone through the CLI. Never request it on your own.
Run `P triage ruling-request --pr N --ids R1-B1,R2-S3`. Your reply says "answer with only `<id>: accept | follow-up | reject`; reasons in another
message" and **ends with the exact `line` it printed**, nothing after it. The owner-go hook records the owner's next prompt against that line. Per
item: `P triage owner-ruling --round R --id ID --decision ACCEPT|FOLLOW-UP|REJECT --reason "<why>" --owner-quote "<the owner's whole answer, copied, never paraphrased>" --pr N`.
A background notice or another session's message between your ask and the owner's answer does not break a pending ruling (the answer binds across them) only while you answer it with tool calls alone: any text in your reply to such a turn voids the pending ask whatever it says (nothing is recorded, ask again), so keep a reply to a notice to tool calls; if you did write text, the owner's answer is refused with a nudge and you show the ask again in your reply to that prompt. One exception (#189): a reply to a task notice or a subagent hand-back that ENDS with the ruling line, with no tool call after it, is itself the pending ask (as if the owner had started that turn); an answer the owner queued while you were busy is refused for such an ask ⇒ ask again. A context compaction between the ask and the answer no longer loses it. A merge request does break (any later reply makes it stale): show it again. An answer the hook could not confirm as typed by the owner is refused (`provenance`) ⇒ ask again.
With `owner_approval: chat` the owner may answer with a click: run `ruling-request --ask` and follow Click-to-approve (below) after the reply's text. A refusal (changed finding text, wrong id, other words, label mode) ⇒ ask again with a fresh `ruling-request`. Recommend first (#771): research the asked items; when ONE bulk ruling is right for ALL of them, add `--recommend accept|follow-up --why <code>` (accept: `real-problem` | `unclear-safe`; follow-up: `minor-later`; the CLI words the why, never yours; there is no reject: the owner can still click Reject all). The CLI shows the recommendation only when the owner-ruling command could record it for every id and, for follow-up, every item is low severity; then the dialog's first option reads `Accept all (Recommended)` / `Follow-up all (Recommended)` and a `Claude recommends …` row sits above the closing line. When the output has `recommendRefused`, or the items need different rulings, pass the neutral dialog as printed, say in your reply that no bulk ruling can be recommended and per-item typed answers may be needed, and never split or re-ask the same items to get a different recommendation. After ANY triage write between the ask and the click (a settle, an arbiter apply, a fix marked implemented), run `ruling-request --ask` again: the content digest covers the finding text only, so an old recommendation would stay clickable. Then re-post `P comment --pr N --kind triage`,
`P followups create --round R`, and the comment again; an ACCEPT is built (its push follows Rule 8), `mark-implemented`, and reviewed in a new round. In label mode, `needsHuman`
items end in `needs-human` (as in step 6): the owner rules outside this session.

## Extra round

**Extra round** (only with `owner_approval: chat`; the owner's `extra round` is the only thing that lifts `review.max_rounds`). When `P state outcome` says
`reachedMax: true` with no `extraRound` and no `grantedRound`: commit and push the fixes (Rule 8 first) and get `verify.quick` green (the grant names the head to be
reviewed), then run `P triage round-request --pr N`. **Trip-wire:** past the limit it may exit 1 `{error: "trip-wire", tripWire, processReview[, longReview][, nextRound]}` with NO `line` (the PR has reviewed `review.max_rounds` + `review.trip_wire_extra_rounds` counted rounds, or `review.trip_wire_not_falling` past-limit rounds accepted at least as many new items as the round before). That is a prompt, not a gate: `P comment --pr N --kind blocked --reason "<processReview.headline>"` (no labels), run-record outcome `blocked` with detail `process-review`, paste `processReview.summary`, and ask the owner (AskUserQuestion: file the open items as follow-ups, `defer-fixes` when eligible / split the PR / one more round). Only "one more round" runs `P triage round-request --pr N --after-process-review` (with `owner_approval: chat`, the full single command `P triage round-request --pr N --after-process-review --ask`: the dialog exists only with both flags in ONE call, and a separate `--ask` call without `--after-process-review` is refused by the trip-wire again), which prints the usual answer and line and still returns `tripWire` and `processReview` (paste them above the line); the owner still types "extra round". Not tripped: unchanged. The normal answer prints `{line, k, n, head, rounds, cost, open, notClean, recommend, why, discard, summary, warnings[, nextRound][, longReview]}`; keep `n`. `summary` also carries the display-only `Prediction:` lines (`nextRound`: what the next round would be, and the no-round alternative of reverting own commits) and, from counted round 6, the `Long review` / `Blocking loop` lines (`longReview`); when `longReview.recommended` is present (on the answer and on the trip-wire refusal) follow it (`stop and park or split` in a blocking loop, whatever `recommend` says) and never argue for another round against it.
Your reply pastes `summary` (the CLI's own plain lines: rounds run, booked cost, open items and their severity, the recommendation), then ONE plain-English paragraph on what is
still open and what the extra round will review (`notClean` says why the review is not clean), and **ends with the exact `line`**, nothing after it. With `recommend: follow-up`
say that first: the open items are all low severity and the accepted fixes can be filed as follow-up issues, taking out the unreviewed commits listed in `discard` (the fixes and
anything else in them), instead of paying for another round. With `recommend: extra-round` never offer the follow-up path. Then wait (or, with `owner_approval: chat`, run `round-request --ask` and follow Click-to-approve below: the dialog comes after that text). The dialog's FIRST option is the recommended one, labelled "(Recommended)", and always the choice the summary's `Recommended:` line names (`Follow up (Recommended)`, `Yes, one more round (Recommended)`, or `No, stop and park (Recommended)` in a blocking loop; `dialogVariant` names which was issued); with no computed recommendation it is the plain `No` / `Yes, one more round` dialog. Never choose for the owner. After a trip-wire process-review prompt in which the owner picked "one more round", `round-request --after-process-review` issues the `round-v2-chosen` dialog (`dialogVariant`): `Yes, one more round (your choice)` first, `No, stop and park` second, no "(Recommended)" label, because the owner already chose the round; when the summary still recommends stopping, say so in plain words before asking, and why. When the owner types `extra round` or clicks "Yes, one more round" ("(Recommended)" is part of the label when the dialog marks it; `Yes, one more round (your choice)` in the `round-v2-chosen` dialog is a granting label too)
the owner-go hook records it against that line and prints a context line; only then run
`P codex-review --pr N --round <n from round-request> …` as in step 1 (it claims the grant after Codex answers; the output shows `grantUsed`). One grant is one
round: if that round accepts items again, ask again or park. A refusal that says the grant "cannot be confirmed as typed by the owner" (#128: the prompt was a harness message, or its transcript entry is gone or elsewhere; #191: or the owner typed it while you were still working, which the hook's one-line note also says) is a refusal too: `round-request` again, show its FRESH closing lines (the same for a "merge": re-run the dry run; for a ruling: `ruling-request`), and the owner types `extra round` themselves after the reply ends. A refusal (`round-cap` "ask again", grant already used, head moved) ⇒ run `round-request` again. Never
type, paraphrase or forge the owner's words, and never run Codex outside `codex-review`. Label mode ⇒ no grant exists: park as before. `review-complete` and the
final gate re-prove the grant from the owner's record on this machine, so finish the review here.

**Past-round approval** (`🔂 Approve past review round #N: round <k> · head <sha12> · repo <owner/name>`). A counted round past `review.max_rounds` that ran before owner grants were recorded (cp #104), or whose grant record is gone, has no grant and can never get one from a new run; `review-complete` and the final gate refuse it. `P triage round-request --pr N --past` prints `{ok, line, k, n, head, past: true, remaining}` for the OLDEST such round. It has no click: even with `--ask` it answers `ask: null, askSkipped` (typed only). Your reply says in plain English that the owner is approving round `k`, which ALREADY RAN at `head` (the review date is not recorded, nothing new is reviewed), and **ends with the exact `line`**, nothing after it. The owner types `approve round` (also accepted: `extra round`, `grant round`, `approve past review round`); the hook records it as kind `past-round` and prints a context line naming the round; then run `P state past-round-grant --pr N --round <n from round-request --past>`. Repeat `round-request --past` while `remaining` is non-empty, then `P review-complete`. The 🔂 line is NEVER used for a new round: a new round is only the 🔁 line and `extra round` (above), and a past-round record cannot start one. Refusals (nothing changed, exit 2) name their remedy: `stale-history` / `history-loss` ⇒ `P state show --pr N` and rerun, `unpublished-history` ⇒ `P comment --pr N --kind triage` and rerun; a failed GitHub publication (exit 3 or `stale-publication`) keeps the saved grant, rerun the same command.
Risk: every grant is proven from the owner's transcript, which Claude Code deletes after 45 days (`cleanupPeriodDays`); a grant whose transcript is gone stops verifying and the PR is refused again. Re-approval through this past-round path is the recovery.

**Follow up instead of a round** (`recommend: follow-up` was shown; only the owner's literal "follow up" or "file follow-ups" starts it, typed or as a hook-verified click on `Follow up (Recommended)`: a question, an unclear answer or silence means wait, and "extra round" is a grant as above). It grants nothing (a click on the button is an instruction the hook verifies; typed words are not hook-recorded): it only lets you do what the rules allow alone, and the owner's later "merge" covers each deferral by name (Rulings rows, below). Steps, in this order:
1. Take the unreviewed work OUT first. `discard` lists the commits after the last reviewed head (`anchor`): revert ALL of them, newest first, one `git revert --no-edit <sha>` each (never `git reset`, never a force-push). A merge commit in the range: restore the tree instead (`git checkout <anchor head> -- .` limited to the PR's own paths, plus deletions) and commit it as "restore reviewed content". The content check in step 3 is the proof either way. Keep the fix head: the `head` the `line` named.
2. Push, run `verify.quick`, and wait until the reverted head's required checks are green: `P ci-wait --pr N` on THAT head (not just `verify.quick`: the head that will merge is the reverted one).
3. `P triage defer-fixes --pr N --ids <the open ids from round-request> --fix-head <the head the line named> --reason "<why they are low severity>"`. It refuses (state untouched) unless the tree is back at the reviewed content, the ids are exactly the unreviewed accepts, each is low severity and was accepted by the judge or arbiter, nothing else is open, and no owner grant exists for the next round: a refusal that names a grant means the owner chose another round, so ask again with a fresh `round-request` and never override it. Do not retry with other ids to get around a refusal.
4. `P followups create --round R` for EACH round it returns (retry after an interruption is safe: filed items are skipped), then `P comment --pr N --kind triage`, then continue to 3 (`review-complete`, the ending). The issues say where the removed fix is (`git diff <reviewed head> <fix head>`): a later PR re-applies it.
5. The deferral rows appear in the merge Rulings block (their own labelled rows after the critical ones, `by claude (round limit)`, `fix removed, NOT in this merge`): say in plain English which fixes were left out and that each is filed as an issue, then ask "merge" for ONE PR per reply (a request for several PRs binds no Rulings block). Claude cannot reopen a deferral (`claude-ruling` refuses it); only the owner's typed `owner-ruling` can.
**After a cap deferral** (`outcome.capDeferred` / `capDeferral.ids` named accepts that `round publish` turned into follow-ups unapplied at the last allowed round, `review.cap_low_accepts`; key on those fields, not on `applied`, which is false on a rerun). `accepted.count: 0` ⇒ no implementer, no push: go straight to step 6 (the outcome reads clean) and name the issues in the hand-off: they are NOT in the PR, and such a PR is never low-risk auto-merged: the gated route refuses it (error `cap-low-owner-go-only`), so ask for the owner's word with `merge --pr N --dry-run --owner-go` and merge with `--owner-go` (that dry run ends at say-merge). They are Rulings rows (`deferred unapplied, NOT fixed in this merge`), so the owner sees them before "merge". If the owner then types `extra round` or "apply them", un-defer ONLY the ids the owner names, never `round-request` first (it still asks on a clean state): `P triage claude-ruling --round R --id <id> --decision ACCEPT --reason "owner asked for the fix" --pr N` for each, then the implementer, push, `P state mark-implemented`, and the automatic extra round follows. Do NOT close the issues: put `Closes #<issue>` in the PR body for each, so an issue closes only when the PR merges (an abandoned attempt leaves it open, nothing to undo). The same `claude-ruling ACCEPT` is the exit when issue filing keeps failing and the filing gate holds the review.
If a later granted round raises the same finding again, link the open follow-up issue in the triage comment instead of filing a second one (`followups create` de-duplicates by fingerprint).

## 3.3 Endings: the merge hand-off

Which ending depends on the item note from 1.5 (as refreshed in step 2):

   - **A `blocking` item** (a blocking hard-stop or test-integrity violation: always under `owner_approval: label`) : NO `Head …` / `🔀` lines
     (`P merge --owner-go` refuses such a diff) and no `needs-human` label. Say the PR is reviewed and CI is green, name what blocks it
     (from `.review/hardstops.json` and `P integrity`), and give the repo's `merge.command` from `P config` with `{pr}` = N and `{sha}` = the head sha
     filled in (EagleWatch: `npm run merge -- <PR> --expect-head <sha>`) for the owner to run.
   - **Protected areas under `owner_approval: chat`** (`ownerMerge` items, nothing blocking): the owner's "merge" covers them. Run
     `P merge --pr N --dry-run --owner-go`; for a `say-merge` with `areas`, name the protected areas in plain English from its `areaIds` (never from the
     agent-writable `.review/hardstops.json`) and end the reply with the closing lines (last bullet). A dry run with blockers ⇒ fix them first; `owner-runs` ⇒ the first bullet.
     `ownerStep.behindNote` (behind main, accepted: base config `merge.behind_base: disjoint`) ⇒ say it in plain English ABOVE the Rulings block when present (else above the closing lines: Areas / Hold / Head), never between the block and the closing lines or between the closing lines: a prose line there voids the binding of the Rulings rows; "merge" still covers only that head and items.
   - **Rulings** (`ownerStep.rulings` present: dismissed BLOCKING or security items and fixes deferred past the round limit (`by claude (round limit)`), single-PR requests only; several PRs with rulings ⇒ a separate reply for each): in plain English, above the closing lines, say what was dismissed and why, naming each item;
     then print the `Rulings <digest12>` block verbatim from the dry run, directly above `Areas` / `Hold` / `Head`. Never type or edit the block: that makes the "merge" bind nothing.
   - **Substitute reviews** (`ownerStep.substitute` present, the `substitute` area: owner-go only; a gated PR is hand-merged by the owner, and label mode never merges one): in plain English, above the closing lines (never between them or inside the Rulings block), say which rounds a Claude stand-in reviewed because Codex's quota was spent or its round budget withheld, by which agent (`round`/`item`, `agent`, `evidence`, `models` from `ownerStep.substitute`), and that the owner's "merge" accepts them. Label mode ⇒ no request: say the PR is reviewed, name the substitute rounds, and that the owner merges by hand.
   - **A `needs-human` hold** (`ownerStep.hold` present, with or without areas): say in plain English that the owner's "merge" also lifts the needs-human hold; report it from the event, `ownerStep.holdInfo` (who added the label, when: the account is shared, so never call it the owner's or yours);
     quote `ownerStep.parkNote.text` only when `parkNote` is present, labelled `pipeline park note (agent-written)`, never as the hold's reason. Never start a prose line with `Hold <x> by`: a Hold-looking line outside the closing lines voids the request.
   - **Click-to-approve.** Under `owner_approval: chat` the "merge" may be a click: run the `--ask` variant of the dry run (several PRs ready at once: the merge-many form) and follow Click-to-approve (last section). Everything above (the closing lines, notes, Rulings, Hold) is unchanged.
   - **Merge as a job.** The owner says "merge" or the hook recorded their click on Merge ⇒ `P job start merge -- node ~/.claude/pipeline/bin/pipeline.mjs merge --pr N --owner-go`, then `P job wait merge --run-id <runId> --timeout 540` until `state` is `done` (it can outlast the Bash tool's 10-minute cap; `replaced`/`lost` ⇒ dry run and `gh pr view` first). Read `exitCode` and `tail`:
     `merged: true` ⇒ done (`holdLifted` names the lifted hold). `error: hold-recovery` with `prMerged: true` ⇒ the PR DID merge (an earlier run's auto-merge fired while recovery disarmed it): report it merged, read the merge commit with `gh pr view N --json mergeCommit`, make no new request. Output with `holdRestored`, `holdKept`, `holdRestoreUnverified`, `holdRemovedByOther`, any other `error: hold-recovery`, or `merge-in-progress` (another P merge of the PR is running, or an earlier run's merge command is still running after that run died; wait and run the dry run again), or `error: lock-timeout` with `reviewLockBusy` (a review writer holds this PR's review lock: wait for it to finish, then run the dry run again) ⇒ nothing merged: tell the owner plainly, show the NEW dry-run lines; `autoMergeDisarmFailed` ⇒ the owner disables auto-merge by hand; a restored hold is a new hold, so the owner must say "merge" again; after `merge-in-progress` or `lock-timeout` the new dry run can change the closing lines, so the owner's earlier "merge" is spent and a fresh "merge" is needed after the new lines.
     `holdRestoreFailed` (`error: hold-restore`) ⇒ the owner re-adds the label by hand; "PR comments unreadable" ⇒ run again later. A changed digest, areas or hold ⇒ show the new lines. **Clean-status retry** (`retryable: 'clean-status'`, the ONLY case where the earlier "merge" is reused): non-queue output with `retryable: 'clean-status'` and no `hold*`, `queue` or `error` field means nothing merged and GitHub refused only because the PR was already clean. Run the dry run WITHOUT `--ask` (`--ask` would issue a new ask): when its closing lines are byte-identical (the complete block: Rulings, Areas, Hold, Head, 🔀), start ONE merge job again without a new "merge" (the record is not consumed, but an expired one is refused: then a fresh "merge" is needed); a second clean-status failure or any changed line ⇒ show the new lines and ask again. Never generalise this to `merge-in-progress`, `queued-behind` or `lock-timeout`.
   - **Queue mode** (dry run `queue: true`; only when GitHub reports a merge queue on the base branch; queue off ⇒ everything above as today). One "merge" enqueues the approved head and GitHub merges it after testing it on top of main and everything ahead of it. No `P update-branch` for "behind" (except the `queue-branch-predates-switch` remedy below), no merge hold, no `Hold` line from a merge hold (a `needs-human` hold is still lifted by the "merge", as above). `ownerStep.queueNote` ⇒ say it in plain English where `behindNote` goes (above the Rulings block / closing lines, never between them). A `queueState` blocker ("already queued at position N" / "already merged") ⇒ report it and make no request. The merge job's output adds `queue, queued, requeued, position, stillQueued, removal`:
     `merged: true` ⇒ as today. `error: queue-removed` (`removal` has the reason and the failing check) ⇒ treat it like red CI: tell the owner, fix (its push follows Rule 8; NO `P redraft` on the removal itself: a draft would make `P merge` refuse a re-queue of the SAME head) → new head → new review and request (after a second removal the owner may re-queue the SAME head with a fresh "merge", e.g. a flake; report it as red CI first). `error: queue-branch-predates-switch` (also the dry run's blocker of that kind, so no request is made; it carries `branchState`) ⇒ the branch's own merge script may not know the queue (it could take "queued" for "merged" and delete the branch): nothing was queued or run. Read `branchState`. `branchState: predates` = the PR's branch does not contain the commit the base names in `.claude/merge-queue-aware` (the commit that taught the repo's merge script the queue): run `P update-branch --pr N` from the PR's own worktree (it catches a predating branch up even in queue mode: `queueCatchUp: true`), `git pull --ff-only`, re-verify, run a review round (base-only), `P review-complete`, then ask the owner again (new head, new request). The catch-up checks the queue again before every update: if the PR was queued meanwhile it ends with exit 1 `queue-entry-live` and no further update. With `updated: true` the head moved: `git pull --ff-only`, do NOT run `P update-branch` again, and tell the owner the PR is queued at a head that has had no review round (a review round or a dequeue by hand). With `updated: false` nothing moved and the queued head is the reviewed one: just report that it is queued. `queue-mode` and `queue-unreadable` can also arrive with `updated: true` (the head already moved): any of these outcomes with `updated: true` means the head moved: `git pull --ff-only`, and the new head needs a review round. `branchState: unknown` = the BASE's marker is the problem (no file, not a full sha, a sha GitHub does not know, or a sha the base itself does not contain): an update cannot help (`P update-branch` answers `queue-mode`, no PUT), so run no update-branch and no review round: tell the owner the base's `.claude/merge-queue-aware` must be added or fixed (the full sha of the commit as it landed on the base), then run the dry run again. A `queue-sweep` re-queue of such a branch ends the record the same way (hold put back, owner told): same split. A failed read (a GitHub error on the marker or the ancestry; a head GitHub does not have, i.e. not pushed yet, counts too) is not a verdict on any path: it answers `queue-unreadable` (the dry run's blocker has that kind, a live record and its hold are kept, the sweep leaves it unsettled), so retry later (push the head first when the detail says it is not on GitHub); no update-branch, no review round. `error: blocked` ⇒ report the stop condition from `problems` (`needs-human` / `pipeline-blocked` label, open `pipeline-pause` / `pipeline-rollback` issue): the PR was dequeued. `queue-unreadable` / `enqueue-failed` ⇒ nothing is queued: say so, show the lines, retry later. `queued-elsewhere` ⇒ another checkout already queued it and the queue sweep carries it on: nothing to do. `requeue-due` ⇒ the live queue record is for ANOTHER head (a different worktree queued it) and its one automatic re-queue is due there. `P merge` never sweeps its own PR, so run `P queue-sweep` right away (do not wait for the scheduled sweep, which only exists on a machine with the LaunchAgent): it re-queues the record from that worktree, or ends it (worktree gone or at another head, hold put back). Report the sweep's outcome for this PR (`requeued`, or `ended` with its terminal; `queuedHead` / `recordRoot` name the record); an `ended` `removed` is red CI. A `queue-removed` that already says the worktree that queued it cannot re-queue it (it is this one, gone, or at another head) needs no sweep: treat it as red CI. A `head-moved` with `adopted` (the PR is in the merge queue at a head nobody approved: the hold is back, the record now tracks that entry and `queue-sweep` keeps it, never merging it on the old approval) ⇒ tell the owner the new head is queued unreviewed and needs a review round or a dequeue by hand. A `head-moved` that says the live queue record here is for another approval changed nothing: run `P queue-sweep`, then `P merge` again.
     `stillQueued: true` ⇒ tell the owner "queued at position N, GitHub merges it" (no new owner step), then relaunch the same `P merge --pr N --owner-go` job: it reconciles (never a second enqueue, never a dequeue, no new "merge") until it ends merged / removed / blocked. After 24 h in the queue, report it to the owner and keep waiting. If the session ends, `P queue-sweep` (a LaunchAgent every 10 min) carries the entry on and notifies the owner.
     One gap stays: a stop condition set after the queue's last check ended but before GitHub merges the group is caught only by the merge job's 90-second poll while a job runs; with no job running the sweep reports the PR as merged under veto after the fact.
   - Any owner command that starts with `gh` is written with gh's absolute path, shell-quoted (`/opt/homebrew/bin/gh …` on this kind of Mac, else `/usr/local/bin/gh`; `command -v gh` when it answers): the owner's `!` prompt shell does not load the PATH that has gh.
   - To preview the verdict before the owner's word, use only `P merge --pr N --dry-run` (add `--owner-go` for that route): same checks, writes and merges nothing; its `ownerStep` says which ending above applies.
     Read the dry run's WHOLE output (or the whole `ownerStep` object). Never pick single keys with `grep`, `--jq`, `jq` or a script, e.g. only `.line`: a filtered read silently drops `ownerStep.rulings`, `areas`, `hold`, `ready` or `behindNote`. A request missing one of them binds nothing, and the owner's "merge" is spent (EagleWatch #1702, 2026-11-06).
     Never run the repo's own merge command (`npm run merge …`, even with `--dry-run`) to preview: the git guard refuses it, and the dry run grants nothing.
   - **Merge hold** (only with `merge.hold_command` in `P config`). Run the dry run of this route first (`P merge --pr N --dry-run`, plus `--owner-go` only on that route); only when `ownerStep.holdEligible` is `true` (code-computed: no blockers beyond the owner-items check that makes it `owner-runs`; `wouldMerge` may be false then) run `P merge-hold --pr N` and add ONE plain-English line above the Rulings block when present (else before the ending) (hold confirmed, other merges pause up to 90 min); the ending stays LAST, unchanged. NOT confirmed (another PR may have taken its hold in between, #181) ⇒ run `P merge-hold --pr N --check` first: `queued-behind` ⇒ the merge-hold blocker ending below (name #A and its expiry, NO `Head` / `🔀` lines, stop: a "merge" there would only be refused and spent); clear ⇒ say in that one line that the hold is NOT confirmed and continue to the ending; `hold-unreadable` ⇒ as below. A `merge-hold` blocker in the dry run: name #A and its expiry (PHT), NO `Head` / `🔀` lines, stop. `hold-unreadable` anywhere: retry once after 60 s, then tell the owner and stop. ## Click-to-approve (only with `owner_approval: chat`; the `--ask` variants)

The owner's "merge", "extra round" and rulings can be a click on a choice dialog instead of typed words. It is the same request with one more call; typing always still works, and it is the fallback.

1. **Run the `--ask` variant** of the command the ending names: `P merge --pr N --dry-run --owner-go --ask`; **several PRs ready at once** ⇒ ONE question: `P merge --dry-run --owner-go --ask --prs a,b[,c,d]` (2 to 4 PRs of this repo, each is dry-run in the worktree that has its branch checked out; its `prs` rows say which are `included` and why not: `rulings`, `hold`, `blockers`, `not-say-merge`, `no-worktree`, `click-off` (that PR's own worktree config has `owner_go.click: off` or is not chat mode: it is approved by typing); an excluded PR gets its own reply and ask); `P triage round-request --pr N --ask`; `P triage ruling-request --pr N --ids … --ask`. Read the output whole, as before.
2. **Print the reply as usual, then ask.** The plain-English summary and the typed closing lines come first and stay the reply's LAST lines of text (from the dry run: Rulings, Areas, Hold, Head, then 🔀 — for several PRs the `#N`-prefixed lines of the merge-many question and its one 🔀 line, `ask.questions[0].question` minus its title; for the extra round and a ruling, the printed `line`): the tab hook and the typed fallback read them. Then, in the same reply, call AskUserQuestion with `ask.questions` **verbatim**: never add `answers`, `annotations` or `preview`, never edit the question text or the options, never call it with a question you wrote yourself. Text you write AFTER the dialog (any) does not move the closing lines: ONLY when the click was refused or unverified and the request is still open, that text must END with that request's own closing line(s) again as the reply's last lines (see the last bullet of step 4), or the owner's typed answer ("merge", "extra round", the ruling pairs) binds nothing; never after a merge job ran or a decline.
3. **`ask: null`** (`askSkipped` says why: label mode, click off, dialog hooks not approved, not a say-merge, blockers, `fewer-than-two-ready`, the ask could not be issued) ⇒ no dialog: the typed request stands exactly as above (for `fewer-than-two-ready`, ask per PR). When the reason is `dialog hooks not approved`, tell the owner once, in plain words, that a click needs `pipeline owner-go approve-dialog-hooks` run in their own terminal.
4. **After the dialog** the owner-go hook gives you one line (as additional context on the tool result) saying what it recorded:
   - "Merge" recorded ⇒ run `P merge --pr N --owner-go` as a job in the SAME turn (Merge as a job, 3.3); several PRs ticked ⇒ one merge job per PR, one after the other.
   - A ruling recorded ⇒ `P triage owner-ruling … --owner-quote "<the quoted answer text the hook line prints, exactly>"` per item.
   - An extra round recorded ⇒ continue with `codex-review --round n` as in Extra round.
   - A follow-up recorded (a line saying the click is recorded: follow up for <repo> #N, "an instruction, not a grant") ⇒ do Follow up instead of a round (steps 1-5 above), never `codex-review`: it admits no round and approves no merge. `defer-fixes` re-checks everything and can refuse; if it does, say why and run `round-request --pr N --ask` again. A line saying the click was "already received" is a replay: do not redo steps already done.
   - A line starting `[claude-pipeline owner-go] the owner's click is received and is verified when it is used` (Claude Code 2.1.323 writes the answer to the transcript only after the hook returns, so the click is only PENDING) ⇒ the answer is not recorded yet and nothing is wrong, but the line does not say which label the owner chose: look at the answer the dialog returned. If it is a declining label (Not yet / No / Not now / No, stop and park / No, stop and park (Recommended)) do NOT run the command: follow the Declined bullet below (the pending decline is settled by the next owner-go read). In a single-choice dialog, text typed into Other counts only when it is EXACTLY the closing words the typed request asks for ("merge", the extra-round words, or per-item rulings for the listed ids): then run the command as for a label (a ruling with that text as its `--owner-quote`); any other typed text ("hold off", "merge after CI") is not an approval: do NOT run the command, follow what the owner wrote. In the several-PR (multiSelect) merge dialog typed text never counts, not even "merge": the hook refuses it (`answer-not-a-label`), so ask the owner to type the closing words instead. Any other label counts as approving (except `Follow up (Recommended)`, below), a ruling's Accept all / Follow-up all / Reject all too (run `P triage owner-ruling` with that label's `--owner-quote`): run the command the line names NOW, in the SAME turn (`P merge --pr N --owner-go`, one per PR ticked for several; `P codex-review --pr N --round <n from round-request>` for an extra round; `P triage owner-ruling` with the `--owner-quote` of the label the owner chose, which the line lists for each label). That command checks the transcript first and acts on any owner approval it can verify that still matches (this click or an earlier one), which is why a declining answer must stop you before you run it. If it refuses, its message may end with notes on owner clicks, each naming its own next step. Follow the note for the ask you just showed (the ask id is in parentheses after the dialog name; a note for another ask id is older: ignore it): `waiting` ⇒ retry once; `declined` ⇒ stop as in the Declined bullet; `could not be verified`, `still unverified` or `could not be read` ⇒ ask the owner to type the closing words; `round k of #N is already used` ⇒ ask the owner for another extra round.
   - Declined (Not yet / No / Not now) ⇒ stop; say in plain English what stays open and that you will ask again when it is ready. `No, stop and park (Recommended)` (the blocking-loop dialog) or `No, stop and park` (the `round-v2-chosen` dialog) ⇒ park the PR per `park-and-rulings.md`, with a dependency-aware split plan, never a carve-out of files.
   - **Pre-revert rule: a pending line for the follow-up dialog** (it says "extra round or follow-up", and the answer the dialog returned is `Follow up (Recommended)`): that is NOT a grant and approves no merge, and never runs `codex-review` (if run by mistake its refusal note says it was a follow-up). Run `P triage defer-fixes` (the arguments of step 3) ONCE BEFORE step 1, i.e. before reverting anything, and read `followUpClick.state` on its answer (the expected refusal is "tree is not back at the reviewed content"): `instructed` ⇒ continue with step 1; `refused`, `unverified`, `waiting` or `none` ⇒ stop, revert nothing, run `round-request --pr N --ask` again and ask the owner to type "follow up"; only after the owner has typed it, pass `--typed-follow-up` to `defer-fixes`, and never otherwise. A refused or unreadable click stays in force across newer asks until the owner's later verified answer on a newer dialog (or the typed override). On a line that says the click is recorded, continue directly (no probe).
   - A line starting `[claude-pipeline owner-go] the click could not be verified (` (the reason follows in the brackets, then `): ask the owner to type the closing words instead`) or no line at all ⇒ nothing is recorded: show THAT request's own closing line(s) again as the LAST lines of text, nothing after them, and ask for the matching typed answer: `merge` for a merge request (the 🔀 block; in this same turn is fine: an identical earlier copy of the block, Hold line included, no longer voids it; a different earlier Hold line still does), `extra round` for an extra-round request (its printed `line`), the `R1-B1: accept` pairs (decision per item) for a ruling request (its printed `line`). For a merge request whose dry-run lines changed (new head or items), run the dry run again and show those instead. If the Hold line itself changed (a new hold event) since the dialog, the same-turn re-show cannot bind (the earlier Hold line is no longer an identical copy): say in plain words that the owner's next message (e.g. "merge") only brings up the fresh request in a new reply, and a "merge" after that approves it.
5. Never answer the dialog for the owner or simulate a click, and the merge hand-off marker rules (`Head …` line directly above the `🔀 Ready to merge …` last line) are unchanged: the typed block is still part of the reply.

## Live-database go

A write to a LIVE Supabase project (every hosted project the owner has not declared `dev` with `P db-refs set --dev`) is not a merge, but it uses the same click-or-type idea. The guard refuses `apply_migration` and every `execute_sql` that is not a `live-db catalog` template until the owner has given a go for exactly that SQL: a click on the dialog below, or (the fallback) the typed `go migration <name>` / `go data <sha12>`.

1. Run `P live-db present … --ask` (`--op migration --pr N --file supabase/migrations/<file>.sql --project <ref> --summary "…"`, or `--op data --sql-file <path> --project <ref> --summary "…"`). It refuses a dirty or unpushed file, a PR head that is not HEAD, a dev ref and SQL it cannot show in full.
2. Write its `block` exactly as printed as reply TEXT, the LAST thing in the reply (nothing after it, no abridged copy; a progress note or a tool result is not reply text, and the text must come after your last tool call of that turn), then call AskUserQuestion with `ask.questions` VERBATIM (never your own dialog, never an `answers` field; never answer it for the owner). The owner clicks `Yes, apply <name>` / `Yes, run <sha12>` or `Not yet`; a click on Yes is verified from the transcript when you attempt the write, and counts only when the reply right before the dialog ends with that same block, exactly as for a typed go (a short wait after the click is normal: retry the call once). When `ask` is `null` (see `askSkipped`), or the hook says a click could not be verified, end the reply with the `block` and wait for the owner to type `go migration <name>` / `go data <sha12>`: a go the owner has neither clicked nor typed is never recorded. A block shown only in a turn a task notice started does not count: show it again in the owner's own turn (see #916).
3. Call `apply_migration` with the file bytes unchanged as `query` and `name` = the file's basename WITHOUT `.sql`. One byte different (a trailing newline, CRLF, a BOM) is a different go. **A numbered migration** (`0261_x.sql`, not a 14-digit date-time version) is never applied through `apply_migration` (it would record a timestamp version and break `supabase db push`): `present` refuses it (`numbered-migration`) and the guard refuses the call without spending a go: tell the owner to run `supabase db push` by hand.
4. **One go per migration file**: two migrations = two block/go cycles. A go is consumed at the attempt and expires after 2 hours; after a failed or interrupted apply, look at the live state read-only (`list_migrations` or a `live-db catalog` query) before asking for a new go.
5. **Data changes** (`execute_sql`): pass the `sql` that `present` printed verbatim as `query` (no BOM, no final newline; a refusal that differs only by those names which and gives both byte counts).
6. **Schema look-ups** go through `P live-db catalog <kind> …` (go-free): pass its `sql` verbatim to `execute_sql`.
7. A migration file containing a literal `\uXXXX` cannot pass (the tool's JSON layer decodes it, so the bytes differ): the owner applies it (with auto-apply on, the same file is refused by both paths).

### Auto-apply after the merge

For a project the owner switched auto-apply on for (`P db-refs show`: `autoMigrations: true`), the guard allows `apply_migration` with NO go for a file a merged PR added, byte for byte, up to 7 days after the merge (spec `docs/specs/2026-11-27-auto-apply-migrations-design.md`). The owner's "merge" is the go. `execute_sql`, data fixes and every other project keep the go above. Auto-apply runs only after the merge, from the PR's merge commit; before the merge nothing is applied.

1. **The merge request.** Only when `P db-refs show` has exactly ONE entry with `autoMigrations: true` whose `repo` equals this repo (case-insensitive) and the PR adds `supabase/migrations/*.sql`: say in plain English, above the closing lines, that merging also applies the migrations to that project right after the merge. Name EVERY migration file, and say which are marked `-- pipeline: apply-after-deploy` (they wait for the deploy; one click too, unless `P db-refs show` has a `deployEnv` for that entry: then the deploy itself is the go and no click is needed, as long as no later commit lands on the default branch first). An after-deploy file that sorts before an unmarked one: fix the numbering (rename) before the merge request.
2. **When, and which commit.** Only on a merged, non-vetoed outcome with a full 40-hex merge sha: the merge job's `mergeSha`; when it is missing (or for `error: hold-recovery` with `prMerged: true`), `gh pr view N --json state,mergeCommit` with `state: MERGED`. Not recoverable ⇒ stop and tell the owner (nothing is applied). A merge reported under a veto (the warning of `merge-queue.mjs` that the PR merged while it was being dequeued for a stop condition, or the queue sweep's report): apply nothing, tell the owner, then the go path on their word. A default branch that is not called `main` changes nothing here: the sha is read, never a branch name.
3. **Which files and bytes.** `git fetch origin <mergeSha>`, then list the PR's migration files from its FULL file list (`gh api repos/<owner>/<repo>/pulls/N/files --paginate`; GitHub cuts that list at 3000 files, so check the FULL list first: 3000 or more entries, or a count different from `gh pr view N --json changedFiles`, means it may be cut short: stop, tell the owner, the go path; only then filter it to `supabase/migrations/` files), never from `git diff <mergeSha>^ <mergeSha>`: a rebase merge puts several commits on the branch and that diff shows only the last one. Keep the files whose `status` is `"added"`, in filename order (any other status, a renamed or removed file: tell the owner, the go path); a file the guard does not accept (it refuses it itself) goes to the go path. The bytes are `git show <mergeSha>:<file>`, never `origin/main`.
4. **Every file goes through the same checks.** (1) State the expected effect: every object the file creates or changes; for a policy its roles, command, predicate and the table's RLS state. (2) Read-only "is it live?" (`P live-db catalog …`; `list_migrations` by name is no proof: the ledger holds `apply_migration` stamps). Live ⇒ skip it and say so. (3) Apply (below). (4) The full effect check: report "applied" only when every part matches; an inconclusive or different result stops the sequence and you tell the owner.
5. **Step (3) per file.** Unmarked ⇒ `apply_migration` with `name` = the file stem and `query` = the merge-sha bytes. Marked `apply-after-deploy` and the entry has no `deployEnv` ⇒ stop the automatic sequence here: wait for the production deployment of `<mergeSha>` (read `P config` `production`: its watch, at most `deploy_timeout_minutes`, in the background with `--interval 60`; a failure, rollback or timeout ⇒ tell the owner, apply nothing). Then, in the PR's worktree (KEEP it until every marked file is applied: the post-merge worktree clean-up skips it) at the PR head, check that `git show <head>:<file>` equals `git show <mergeSha>:<file>` byte for byte (different ⇒ stop and tell the owner), run `P live-db present --op migration --pr N --file <file> --project <ref> --summary "…" --ask` and the dialog above; on the owner's go, `apply_migration`; then the next files. Marked and the entry HAS `deployEnv` ⇒ the same wait for the production deployment and the same byte check, then call `apply_migration` directly (the guard reads GitHub's deployment itself: no dialog); a deny naming the deploy (not finished, another commit, not the registered bot) ⇒ take the dialog path above, or call again once the deploy shows as finished; a deny saying a later commit is on the default branch is final (any commit after the merge takes the click: no new call helps), so take the dialog path. A SUCCESS deployment means built and assigned, not serving: when production is rolled back or auto-promotion is off, tell the owner to run `pipeline db-refs after-deploy off --ref <ref>` first and take the dialog path.
6. **A refusal or failure** stops that PR's remaining files: 🚨 tell the owner (the new code is live without that schema), take a read-only look at the live state, then the go path. Rolling the code back and repairing the database are separate owner decisions. A failed or interrupted auto-apply is never retried automatically: the next attempt needs a go given after it.
7. **Files that cannot take the gap.** A migration that must be live before its code deploys, or that cannot take a failed apply after the merge: the go before the merge, or its own PR. DO-wrap a top-level `DROP` in the file itself. A literal `\uXXXX` in a file: the owner applies it.
8. **The report** names the machine that applied (the attempt history is per machine) and points at `P live-db auto-log`.

Details of the guard: `docs/cli.md` section "Live database guard".
