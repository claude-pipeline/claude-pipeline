# 3. Review complete, ready, hand-off

The full section 3.

## 3. Review complete, ready, hand-off

1. `P review-complete --pr N` (HEAD pushed and equal to the PR head). Exit 0 posts the marker comment and takes `awaiting-review` off. Exit 1 ⇒ read
   `reason` (a commit since the last round, an unmarked ACCEPT, a Fable pass owed) and go back to the round it names. A reason naming `fable-refresh` (a Fable proof below the newest Fable) ⇒ `P state fable-refresh --pr N` (an uncounted Fable-only round on the pushed head), then 2.4 for that round (the pass reviews the whole PR diff), 2.5 and 2.6 as usual, then `P review-complete` again. A reason `behind-base` (a draft behind its base) ⇒ run its `remedy` (`P update-branch --pr N`, `git pull --ff-only`, the baseOnly `codex-review` round, `review-complete` again) BEFORE `gh pr ready`, so CI runs once on current main. Any later commit that changes
   the code needs another round and another `review-complete`; push it per Rule 8. **Freeze after clean:** once `P state outcome` is clean for the pushed head, commit nothing that changes reviewed content except a CI-required fix, a conflict merge made alone (Queue mode, below) or a change the owner names; say BEFORE pushing such a commit that it costs a review round (and, past the limit, an owner grant). A FOLLOW-UP decision becomes an issue (`P followups create`) whatever its bucket; ACCEPTs are always fixed; WORTH CONSIDERING is a bucket, not a decision. No test is written after the fact to settle an item already REJECTED or FOLLOW-UP. The undo: after a clean round, reverting the later own commits (newest first, `git revert`, never reset or force-push) restores the reviewed content and needs no round. One exception: commits after the last round that ONLY ADD lines to `review.docs_exempt_paths` documents (`P config`) need no round, and each added line must be a strict ledger row (`` | 0240 | `name` | YYYY-MM-DD | #PR | | ``, last in the file, numbers rising, for a migration at the reviewed head); anything else, or a listed document an instruction file `@`-imports, takes a round;
   `review-complete` posts for the current head (`docsExempt`), a refusal names the file that forces a round. Verification of that head is still owed.
2. Only after that exit 0. If the head changed since 1.5 ran (any review fix), re-run 1.5 on it first: the label below, the CI reading and 3's ending use its notes.
   High risk (1.5's `P risk`) ⇒ `gh pr edit N --add-label <ci.e2e_label>` (if configured); then `gh pr ready N`.
   CI runs now and is the full proof. Wait with `P job start ci -- node ~/.claude/pipeline/bin/pipeline.mjs ci-wait --pr N`, then
   `P job wait ci --run-id <runId> …` again until it is done. To read ci-wait's JSON, finish with `P job wait ci --run-id <runId> --full` (or `job read --full`) and read `output` (stdout only): `tail` is the last 40 lines of stdout AND stderr, so it can start with a `ci-wait: …` progress line or in the middle of the pretty-printed JSON. Never `gh pr checks --watch` here: right after `gh pr ready` a required
   check's only result is the draft-era SKIPPED one, which `gh` counts as passed (Phase 6: hand-off 14 min early); ci-wait waits for
   every required check of the base branch to report after the PR became ready. Its `verdict` when not ok: `failed` ⇒ implementer fix, pushed per Rule 8 with `--reason ci-failed`
   (below; a ready-era failure of an attempt a re-run has superseded is waited on, so `failed` is the newer attempt's own result, unless its message says "superseded by a newer attempt that never reported": then the superseded failure stood at `--appear-timeout` and no newer result replaced it); `head-moved` / `base-changed` ⇒ back to step 1 of this section; `draft` ⇒ the PR is a draft: this session skipped or lost the ready step (it ran `P redraft` itself, or never readied) ⇒ back to step 1 of this section; this session did NOT draft it (another session's redraft, or the owner drafted it by hand) ⇒ do not mark it ready; with `merge.hold_command` in `P config` first `P merge-hold --pr N --release --reason handoff-withdrawn`, then tell the owner and stop; `missing` / `stale-skipped` (a required check never ran on the ready event: ci-wait only says `missing` once no run that could produce the check is still going on the head (a ready-era run, or one started before ready: `heldBy.predatesReady`), and `stale-skipped` once nothing created or (re-)started after `gh pr ready` is still running, since a `needs:`-gated aggregate appears late by design; `heldBy` in the output names the run it was waiting on),
   `conflicting` (a required check never appeared and the PR CONFLICTS with its base: GitHub runs no workflow on such a PR, so this is not a CI problem: do not hunt for one) ⇒ merge the base as ONE merge commit and review it in its own resolution round (`reference/special-rounds.md`, "Conflict with the base", incl. a pre-push hook that refuses the lone merge), then back to step 1 of this section,
   `unverified` (branch protection or rules unreadable), `no-required-checks`, `timeout` ⇒ tell the owner in plain English, with the
   check names, and wait. `owner_approval: label` with a blocking item noted at 1.5: run it with `--wait-all`; the guard checks
   reporting just those items are expected to be red — that is not a fix target: park (section 2) once ci-wait shows every other check
   green. Any other red ⇒ implementer fix, push (Rule 8), back to step 1 of this section. With `merge.hold_command` in `P config`, a `failed` verdict first releases this PR's merge hold:
   `P merge-hold --pr N --release --reason ci-failed` (a red PR must not keep the merge line; it acts only on N).
   A `passed` check flagged `predatesReady: true` rests on a run or status from before `gh pr ready` (a draft-era pass), and `predatesReady: null` on a status whose Actions run could not be read (unresolved: treat it as flagged); while a guard check is flagged, run the ci-wait job again (about a minute apart, at most 5 times in all): the ready-event guards run re-posts that check, and a flagged result again means it has not reported yet. Hand off once the guard check is no longer flagged; if it is still flagged after the 5th run, tell the owner the guard never re-reported on the ready event and do not hand off as clean.
   `passed` on a `ci.e2e_label` PR also carries `others` (non-required checks of the head that are still running or red; `others: []` = none). A running entry (`queued`, `in_progress`, `pending`) ⇒ the suite the label asked for is not done: do not hand off yet. Start the ci-wait job with `--wait-others` on a `run-e2e` PR: it keeps waiting until no entry is running; at its `--timeout` it returns `passed` with the still-running entries in `others`, which still means do not hand off: start the job again (without it, run the same ci-wait job again every few minutes, `job wait` as above). A red entry ⇒ the e2e suite itself: treat it as `failed` (implementer fix, Rule 8 `--reason ci-failed`); any other red non-required check ⇒ name it to the owner in the hand-off. `ci.merge_checks` (checks the repo's own merge command needs although protection does not, e.g. EagleWatch `Replay from zero`) are waited on by ci-wait itself like required checks when they report (`checks[].source: "merge_checks"`); one with no producer at all (a path-filtered workflow that did not run) comes back as `notOwed` on a `passed` verdict (or on a `--wait-all` `failed` one, left out of `checks` either way): it is not owed, nothing to wait for, and not a check that is missing.
   Base moved ⇒ `P update-branch --pr N`, `git pull --ff-only`, review again if content changed. With `merge.hold_command`, update-branch takes this PR's merge hold right
   before the update (output `hold`), so another PR's merge cannot undo the catch-up's CI round. The hold stays through that pipeline-made head (`P merge-hold --release --reason new-commits`
   answers `kept: own-successor` for it; after your push Rule 8 already released the hold, so `new-commits` is only for a push made without `P redraft`). update-branch releases the hold itself on `checks-failed` (`ci-failed`) and `rebase-needed` (`update-conflict`):
   `holdRelease` not `confirmed` ⇒ run that release once yourself, from this PR's own worktree on its branch (a provider may refuse a release from any other checkout or a detached HEAD: EagleWatch does). `head-timeout`, `checks-timeout`, `cycle-cap`, `head-moved` keep it (retry, or re-read: a PR-side push ⇒ the `new-commits` release).
   `outcome: "queued-behind"` (another PR's older merge hold is ahead; `blockedBy`, `doNotUpdate`) ⇒ never update past it; wait your turn:
   `P job start turn -- node ~/.claude/pipeline/bin/pipeline.mjs merge-hold --pr N --check --wait` (one check every 5 min, up to 120 min), `P job wait turn --run-id <runId> --timeout 540`
   until done. `outcome: "front"` ⇒ `P update-branch --pr N` again. `timeout` / `unreadable` ⇒ `P merge-hold --pr N --release --reason queued-behind`, report it as in 3's
   **Queued behind** and stop. `hold-unreadable` ⇒ retry once after 60 s (a confirmed hold is kept, `holdTaken: true`; a take that may have half-written one is already released: `holdRelease`), then tell the owner and stop
   (with `holdTaken: true`, first `P merge-hold --pr N --release --reason hold-unreadable`).
   **Queue mode** (`P update-branch` answers `outcome: "queue-mode"`, the dry run says `queue: true`): it exists only when GitHub reports a merge queue on the base branch, which tests the PR on top of main and everything ahead of it. A moved base is no problem there: no `P update-branch` for "behind", no merge hold (`P merge-hold` answers `queueMode: true`), no catch-up CI. One exception, only for a custom `merge.command` and a PR that is not queued yet (the default command and a queued PR always get `queue-mode`): a branch that does not contain the commit the base names in `.claude/merge-queue-aware` (the commit that taught the repo's merge script the queue) may carry a merge script that does not know it (a custom `merge.command` runs the branch's own script), so `P merge` and the dry run refuse it as `queue-branch-predates-switch`; there `P update-branch --pr N` DOES catch it up in queue mode when the refusal says `branchState: predates` (output `queueCatchUp: true`; no merge hold), then `git pull --ff-only`, re-verify, a review round (base-only), `P review-complete` and ask the owner again. The catch-up re-checks before every update and stops once the branch holds the marker commit (`up-to-date`, even with the base moved again). If the PR gets queued meanwhile it answers `queue-entry-live` (exit 1) and makes no further update. With `updated: true` the head moved: `git pull --ff-only`, do NOT run `P update-branch` again, and tell the owner the PR is queued at a head that has had no review round (it needs one, or a dequeue by hand). With `updated: false` nothing moved and the queued head is the reviewed one: just report that it is queued. `queue-mode` and `queue-unreadable` can also arrive with `updated: true` (the head already moved): any of these outcomes with `updated: true` means the head moved: `git pull --ff-only`, and the new head needs a review round. For `branchState: unknown` (the base's marker is missing, malformed, names a commit GitHub does not know or names a commit that is not on the base) an update cannot help: `P update-branch` answers `queue-mode` with no PUT and the marker on the base must be added or fixed (no review round); a GitHub read error answers `queue-unreadable` (the dry run's blocker has that kind too, not the predates one): try again, and a head GitHub does not have (not pushed yet) says to push it first. `owner-merge.md` (Merge as a job) has the merge-job outcomes. Queue off ⇒ everything above as today.
   **Queue mode: do not bring the default branch in.** Never merge or rebase the default branch into the PR branch to stay up to date. The queue test is read-only: `P merge --pr N --dry-run` answers `queue: true` (or you already have a `queue-mode` answer); never run `P update-branch` just to find out (it updates the branch and writes run records, and outside queue mode it also takes a merge hold; in queue mode it updates a branch that predates the queue switch); unreadable ⇒ unknown, not queue-off. Merge it only when GitHub reports the PR `CONFLICTING` (`gh pr view N --json mergeable`) or an installed pipeline command refuses and names a catch-up of the default branch that is not a pipeline remedy (do not run a mutating command to find one; the `queue-branch-predates-switch` refusal is not such a case: its remedy is `P update-branch --pr N` above, never a hand merge), and only once the review is otherwise clean. Exception to "clean first": a diagnosed base-side prerequisite that blocks the review or a required check, e.g. a trusted `review.codex_model` fix that must come from main (SKILL.md rule 2 / section 0), a required check that cannot run or pass here without an identified base-side workflow or dependency fix (a workflow merely changing on main is NOT a reason), or a diagnosed merge-group integration failure (a duplicate migration number, incompatible schema or auth assumptions: that needs a real fix and validation; merging main alone may not solve it). Do it by hand as ONE merge commit of `origin/<default_branch>`: resolve each conflict by keeping lines from one side (no newly written lines), touch no other file (no regenerated lockfile or types, no fix folded in), push it (Rule 8) and run its own round BEFORE any other commit, so the resolution-only proof (`git.mjs#resolutionReviewBase`) may qualify: a real review, not counted, no grant. The pipeline decides: escalation, untrusted anchors or unsupported git can still force a broader review, so never promise it passes. If it cannot qualify (rename/delete, add/add, binary, mode or attribute conflicts, or the resolution needs new lines), say why and that it costs a counted whole-PR round BEFORE asking; correctness beats the free round: write the resolution the conflict needs and accept the counted round, never pick side lines just to get an uncounted one. Never rebase a reviewed branch: the proof needs the last reviewed head on the first-parent chain.
3. **STOP** (outcome `awaiting-owner-merge`; `owner_approval: label` with a blocking item parks instead, no merge request): run the stop ritual first, then tell the owner in plain English what changed, the PR link, the review outcome and follow-up issues.
   Then Read `reference/owner-merge.md` (section 3.3) and end the reply exactly as it says: which ending applies depends on the item note from 1.5 (as refreshed in step 2)
   (a `blocking` item ⇒ the repo's `merge.command`; otherwise `P merge --pr N --dry-run --owner-go` and its closing lines). The owner says "merge" (typed, or a click the owner-go hook recorded: `reference/owner-merge.md` section Click-to-approve, run the dry run as `--ask`; several PRs ready ⇒ one `--ask --prs a,b` question) ⇒ `P merge --pr N --owner-go` as a job
   (`P job start merge -- …`), never `gh pr merge` yourself. The block order is Rulings (when present), Areas, Hold, Head, 🔀; copy it from the dry run, never type the digest. Read the dry run whole: grep or a single-key `jq` drops the Rulings block. The closing lines look like:
   `Head <sha12> · items <digest> · repo <owner/name>`
   `🔀 Ready to merge #N — say "merge"`

A migration that must reach a LIVE database is applied only with the owner's go (a click, or the typed fallback): `reference/owner-merge.md` section "Live-database go".
